# Лабораторная работа № 2. Реализация объектной модели

Прототип платформы для создания и редактирования коротких видеороликов на Python и PySide6 по предоставленной спецификации.

## Запуск

Требуются Python 3.12+ и [uv](https://docs.astral.sh/uv/). Из каталога проекта:

```bash
uv run video-editor
```

uv создаст виртуальное окружение и установит зависимости из `uv.lock`. Альтернативная точка входа:

```bash
uv run python -m video_editor
```

Другой каталог для сохранённых проектов можно указать явно:

```bash
uv run video-editor --data-dir ./my-projects
```

## Возможности прототипа

- Список проектов: создание, открытие, удаление и выход из приложения.
- Редактор: добавление видео и аудио через отдельные окна, размещение материалов на временной шкале, выбор видеоклипа, обрезка, разделение, перемещение и добавление текста.
- Окно экспорта: выбор формата, разрешения, частоты кадров и пути сохранения, запуск демонстрации, отмена и возврат в редактор.
- Возврат из редактора к списку проектов. Структура проекта сохраняется кнопкой «Сохранить» и при закрытии редактора.

Чтобы разместить импортированный файл на шкале, дважды нажмите на него в списке медиаматериалов. Для изменения видеоклипа сначала выберите его на шкале. Закрытие окна редактора сохраняет проект и возвращает к списку проектов.

В `data/projects/*.json` сохраняются **структура проекта и пути к исходным файлам**, а также положения клипов, границы фрагментов и текст. Видео и аудио в JSON не записываются, не копируются и не изменяются; для дальнейшей работы исходные файлы должны оставаться по сохранённым путям.

Обработка медиа не реализована, что допускается заданием. Все импортированные материалы получают условную длительность 10 секунд и стандартные метаданные. Экран предпросмотра остаётся чёрным; кнопка воспроизведения вызывает сервис предпросмотра и обновляет сведения во всплывающей подсказке экрана. Экспорт демонстрирует работу окна и вызов сервиса, **не создаёт видеофайл** и не сообщает о фактическом успешном экспорте. FFmpeg не требуется.

## Соответствие объектной модели

Реализованы все классы **базовой модели** из раздела 6. Имена методов сохранены в стиле UML (`createProject`, `getTimeline` и т. д.). Направления развития из раздела 7 — эффекты, субтитры и шаблоны — относятся к будущим расширениям и в базовую версию не включены.

| Слой / файл в `src/video_editor/` | Классы |
| --- | --- |
| Model — `model.py` | `VideoProject`, `Timeline`, `TimelineItem`, `VideoClip`, `AudioClip`, `TextOverlay`, `MediaFile`, `VideoFile`, `AudioFile`, `ExportSettings`, `PreviewResult`, `ExportResult` |
| Интерфейсы — `contracts.py` | `IProjectRepository`, `IMediaRepository`, `IPreviewRenderer`, `IVideoExporter`, `IView` |
| Logic — `logic.py` | `ProjectService`, `MediaService`, `EditingService`, `PreviewService`, `ExportService` |
| Presentation — `presentation.py` | `BaseView`, `ProjectListUI`, `ProjectEditorUI`, `ExportUI` |
| Infrastructure — `infrastructure.py` | `LocalProjectRepository`, `FileMediaRepository`, `PreviewRenderer`, `VideoExporter`, `DependencyContainer` |
| Фабрики Infrastructure — `factories.py` | `ServiceFactory`, `UIFactory` |
| Точка входа — `application.py` | `Application`, `ApplicationConfigurator` |

`ApplicationConfigurator` регистрирует адаптеры, сервисы и окна в `DependencyContainer`; фабрики создают объекты с зависимостями через конструкторы. `Application` связывает окна сигналами Qt и устанавливает текущий проект для сервисов. Интерфейсы реализованы через абстрактные классы. Абстрактный `BaseView` реализует `IView`, конкретные окна переопределяют `refresh()`.

Для недетализированных мест добавлены общий `MediaImportDialog` для двух окон импорта, получение списка проектов (`findAll`, `listProjects`), обработчики навигации и сохранения, а также `ExportSettings.outputPath`. Параметры операций, вынесенные в UML в секции полей, перенесены в сигнатуры по диаграмме последовательности. Имена и наследование классов базовой модели сохранены; это дополнения для выполнения показанных сценариев интерфейса.

Публикация на GitHub и коммиты не выполнялись.

## Анализ ошибок исходной модели

Анализ спецификации «Платформа для создания и редактирования коротких видеороликов» (`report.pdf`) и приложенной BPMN-схемы (`bpmn.svg`) по критериям приложения 3. Ниже приведены 7 существенных и 5 менее существенных замечаний. Номера разделов и рисунков относятся к исходному отчёту.

## Существенные ошибки

### 1. Параметры операций записаны как атрибуты классов

**Где:** разделы 6.2–6.4, рисунки 6–8.

В `EditingService` параметры `clipId`, `startTime`, `endTime` и другие вынесены в секцию атрибутов, а операции записаны как `trimClip(): void`, `splitClip(): void` и т. п. Аналогично оформлены `ProjectEditorUI`, `Timeline.replaceClip()` и `TextOverlay.create()`. При этом диаграмма последовательности передаёт этим операциям аргументы: например, `trimClip(clipId, startTime, endTime)`.

В результате диаграммы задают разные контракты одних и тех же методов. Нужно вернуть параметры в сигнатуры операций, убрать их из полей и согласовать вызовы между диаграммами. Поля вроде `videoFile: VideoFile` также нарушают требование показывать ссылки на разрабатываемые классы через отношения.

**Критерии:** 6.4, 7.16.

### 2. Направления развития требуют изменения существующих классов

**Где:** разделы 7.1–7.3, диаграммы видеоэффектов, субтитров и шаблонов.

От существующего `EditingService` проведены зависимости к новым `EffectsService` и `SubtitleService`, а от существующего `ProjectService` — к новому `TemplateService`. Кроме того, у `VideoClip` появляется связь `effects`, у `Timeline` — `subtitleTracks`, у `DependencyContainer` — ссылки на новые фабрики.

Таким образом, старые классы должны получить знания о новых классах и дополнительные связи. Это противоречит требованию развивать систему без изменения базовых классов. Следует предусмотреть точки расширения через интерфейсы, наследование или отдельные компоненты, использующие базовую модель.

**Критерии:** 7.13, 7.14.

### 3. Окна импорта не сопоставлены с классами и обработчиками

**Где:** раздел 6.4, рисунок 8; раздел 9.4, рисунки 17–18; раздел 10, рисунок 19.

В макетах и диаграмме состояний есть окна «Добавление видео» и «Добавление аудио», но в модели представления не указано, какие классы их отображают. Не описаны и обработчики выбора файла, подтверждения импорта и отмены. Методы `ProjectEditorUI.addVideoClip()` и `addAudioClip()` относятся к добавлению клипов на шкалу; на диаграмме последовательности они получают уже существующие медиаобъекты.

Нужно указать ответственные UI-классы и методы, связывающие действия этих окон с `MediaService.addVideoFile(path)` и `addAudioFile(path)`.

**Критерии:** 7.9, 8.4.

### 4. Часть действий интерфейса не обеспечена методами UI-классов

**Где:** раздел 6.4, рисунок 8; разделы 9.2 и 10, рисунки 15 и 19.

На макете редактора есть кнопки «Сохранить» и «Экспорт», а на диаграмме состояний — переход «Закрыть проект». В `ProjectEditorUI` отсутствуют соответствующие обработчики. В `ExportUI` также нет обработчика отмены, хотя кнопка и переход предусмотрены. Не показано, каким способом редактор вызывает сохранение проекта и открывает окно экспорта.

Следует сопоставить эти действия с методами UI-классов и необходимыми связями между компонентами.

**Критерии:** 7.9, 8.4.

### 5. Выбранный путь экспорта не передаётся модулю экспорта

**Где:** разделы 6.2–6.5, рисунки 6–9; раздел 9.3, рисунок 16.

Окно экспорта позволяет выбрать путь сохранения файла. Однако `ExportSettings` содержит только `format`, `resolution` и `frameRate`, а `ExportService.exportVideo(settings)` принимает только эти настройки. В контракте `IVideoExporter` предусмотрены проект и настройки, но путь назначения тоже отсутствует. Поле `ExportResult.outputPath` описывает результат операции и не задаёт входной путь.

В модели не определено, как пользовательский выбор доходит до экспортера. Нужно добавить путь в настройки либо в параметры операции.

**Основание:** несогласованность макета интерфейса и контрактов классов; критерий 7.9.

### 6. Не описано получение списка сохранённых проектов

**Где:** разделы 6.3–6.5, рисунки 7–9; раздел 9.1, рисунок 14.

`ProjectListUI.showProjects()` должен отображать сохранённые проекты с названиями и датами изменения. При этом `ProjectService` предоставляет только создание, открытие, сохранение и удаление, а `IProjectRepository` и `LocalProjectRepository` — поиск по идентификатору, сохранение и удаление. Операции получения списка нет ни на уровне сервиса, ни на уровне хранилища.

Сценарий начального окна не обеспечен контрактами классов. Нужно определить получение списка и передачу данных в `ProjectListUI`.

**Основание:** несогласованность интерфейса и модели классов; критерий 7.9.

### 7. ER-диаграмма не содержит центральную сущность «Видеопроект»

**Где:** раздел 3.1, рисунок 1; текстовое описание в разделах 1.2–1.4.

Текст определяет видеопроект как сущность, объединяющую медиаматериалы и временную шкалу, которую можно сохранять и повторно открывать. На ER-диаграмме показаны шкала, клипы, файлы и текстовые элементы, но самого видеопроекта и его связей нет.

По этой диаграмме нельзя определить принадлежность шкалы и исходных файлов конкретному проекту. Нужно добавить сущность «Видеопроект» и соответствующие отношения.

**Критерий:** 3.1.

## Менее существенные ошибки

8. **Не у всех ассоциаций указаны кратности.** Например, на рисунке 6 у связи `VideoProject — MediaFile` указано `0..*` со стороны файлов, но отсутствует кратность со стороны проекта. На рисунке 7 у связей `EditingService — Timeline` и `ProjectService — VideoProject` кратности не указаны. Нужно проставить их на обоих концах. **Критерий: 7.3.**

9. **Не обозначены классы данных.** У `ExportSettings`, `PreviewResult` и `ExportResult`, содержащих только поля, отсутствует стереотип `<<data>>`. У `VideoProject` он есть на обзорной диаграмме, но отсутствует на детальной. Нужно согласовать обозначения. **Критерий: 7.17.**

10. **Одни и те же сущности названы на разных языках.** Например, в тексте и ER-диаграмме используются «Видеоклип» и «Временная шкала», а в UML — `VideoClip` и `Timeline`. Следует выбрать единый язык имён сущностей для текста и диаграмм. **Критерии: 1.4, 1.5.**

11. **Не обозначены переопределения методов представлений.** На рисунке 8 `ProjectListUI`, `ProjectEditorUI` и `ExportUI` наследуются от абстрактного `BaseView` с методами `show()` и `refresh()`, но не указано, какие из них переопределяются. Нужно явно показать переопределяемые операции либо уточнить, что наследники используют общую реализацию. **Критерий: 7.6.**

12. **Не раскрыт способ доступа к объектам для зависимостей `use`.** На рисунке 10 `Application` использует три UI-класса, но у него нет соответствующих ассоциаций или параметров методов. Аналогично `ApplicationConfigurator` использует `ServiceFactory` и `UIFactory` без показанного способа получения объектов. Следует обозначить передачу зависимостей или хранение ссылок на них. **Критерий: 7.11.**
